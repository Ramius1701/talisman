# Development architecture and storage

## Component map

| Component | Primary responsibility / entry points |
| --- | --- |
| Servo | Listener, session process/node assignment, IP admission and event runner; `Servo.cpp`, `EventMgr.cpp` |
| Talisman | Terminal BBS session; `main.cpp` -> `Node::run` |
| Config | INI and core TOML load, security levels, themes and protocols |
| Menu | Menu load/filter and command dispatch |
| User | SQLite identity, attributes, subscriptions and last-read values |
| MsgConf / MsgArea / MessageReader | Squish conference/area access, posts and terminal reader |
| FileConf / FileArea / Protocol / Archiver | File indexing, payload operations and external transfer/archive processes |
| Editor / FullScreenEditor / AnsiEditor | Message/editor UI and external editor integration |
| Script | Lua C bindings and per-invocation script states |
| Common | Shared INI/TOML helpers, Squish format implementation, logger and supporting code |
| Toolbelt | Operator commands, file indexing/conversion and message maintenance |
| Postie / Binki | FTN tossing/TIC and BinkP transport |
| Falcon / Qwkie / Bridge | WWIV, QWK networking and base-to-base bridging |
| Gofer / NewsSrv / HttpSrv / Trinket | Optional service/integration components |

Start at [Node.cpp](../../Talisman/Node.cpp), [Menu.cpp](../../Talisman/Menu.cpp) and [Script.cpp](../../Talisman/Script.cpp) for user-visible behavior, [Servo.cpp](../../Servo/Servo.cpp) for connection lifecycle, and [Common/Squish.cpp](../../Common/Squish.cpp) for message serialization. Components often have their own `Config`, `User` or `Archiver` class; changing one does not automatically change the others.

## Persistence

| Artifact | Role / source |
| --- | --- |
| `<Data Path>/users.sqlite3` | `users`, `details`, `lastr`, `subs`; [User.cpp](../../Talisman/User.cpp) |
| `<Data Path>/email.sqlite3` | Local private mail; [Email.cpp](../../Talisman/Email.cpp) |
| `<Data Path>/call_log.sqlite3` | Caller session/counter history; [CallLog.cpp](../../Talisman/CallLog.cpp) |
| `<Data Path>/<area database>.sqlite3` | File metadata/index; [FileArea.cpp](../../Talisman/FileArea.cpp) |
| `<Message Path>/<base>.sqd`, `.sqi` | Squish payload/index; [Squish.cpp](../../Common/Squish.cpp) |
| `<Temp Path>/<node>/` | `node.use`, `node.msg`, `NODECHAT.TXT` and door dropfiles; [Node.cpp](../../Talisman/Node.cpp), [Door.cpp](../../Talisman/Door.cpp) |
| Download directories | File payloads independent of SQLite indexes |
| Network inbound/outbound directories | Mail/file packets, queues and transport state |
| `<Data Path>/ssh_host_*_key` | SSH host keys generated by [main.cpp](../../Talisman/main.cpp) |

`users` has `id`, case-insensitive unique `username`, `password`, `salt`; `details` stores `uid`, `attrib`, `value`; `lastr` stores `uid`, `msgbase`, `mid`; `subs` stores `uid`, `msgbase`. The tables are created with `CREATE TABLE IF NOT EXISTS`; this checkout does not implement the newer workspace's shared schema migration/identity service. Attribute strings also include security level and terminal preferences.

The legacy credential function computes uppercase hexadecimal SHA-256 of `password + salt`; salt is generated from ten random bytes and encoded as uppercase hexadecimal. See `User::hash_sha256` and `update_password`. Preserve this format when reasoning about compatibility. A future password-format change must update every authentication consumer, including Toolbelt and optional services, rather than changing the session alone.

Before changing storage, make a consistent backup of an inactive development installation, including SQLite data, complete Squish base pairs, payloads, INI/TOML/assets and network state. Restore and test that backup in a separate installation. This is a recommended development procedure, not a backup/recovery feature implemented by Talisman. Do not copy only one file from a live SQLite database or only `.sqd` from a base being modified.

## Extension workflow

1. Identify the component, parser/dispatcher and persistence affected by the change.
2. Preserve existing on-disk semantics or specify an explicit migration with fixtures and rollback limits.
3. Add the behavior in the source, with meaningful tests for the affected boundary (malformed config, actual transfer bytes, access checks or storage consistency as applicable).
4. Update prose and examples with the same change; regenerate references and review their diff.
5. Record platform, revision, build dependencies, commands and observed runtime results in the validation ledger.

For a new menu action, review Menu's level filtering and the operation's own checks. For a Lua binding, validate arguments explicitly, define return/error behavior and add it in `Script::init_state`. For a new INI key, document exact spelling and each consumer's default. For a network feature, trace scanner -> transport -> tosser and test queues and duplicate handling separately.

The preserved repository has no existing automated test suite or root CI build entry point established by this review. Tests/build improvements in the separate BBS workspace are not proof for this revision. [Known discrepancies](validation.md) identify promising first fixes without changing behavior during documentation reconstruction.
